# Linux server black-box acceptance report (#140)

## Result

The Ubuntu run reproduces the [macOS result](140-main-3877600.md): the real
Target Service receives Observation messages but emits no matching Target on
`targets.updated` within the eight-second acceptance budget. Five scenarios
fail at this common prerequisite. The later probability, deduplication,
validation, decay and redraw assertions are not reached; these results do not
establish five independent defects.

The separate real DBMS SQL protocol control passes. SQL integration remains
blocked by an unconfigured launch/schema contract. Existing smoke regressions,
the documented CLI, formatting and static checks pass. No production code was
changed and nothing was pushed to GitHub.

signal checks cover the old smoke scenario, not interruption of the new DBMS path.

## Failure evidence and comparison

Each failed server case records:

```text
ACCEPTANCE: no server-produced targets.updated for 17 within 8s; sent only Observation, no Target injection
```

The real service logs successful Observation receipt repeatedly; bootstrap retries
reuse the same observer and timestamp. The Map case records:

```text
0 visible, 0 outside map
Map shown. Close the window or press Ctrl+C to exit.
Broker connected; SUB targets.updated sent (protocol has no acknowledgement)
```

This reproduces finding F-01 from the macOS report on Linux. No additional
Linux-specific functional failure was observed in the exercised paths. The
SQL contract gap C-01 also remains unchanged. The run provides no evidence that
the later aggregation/validation/decay assertions would pass once publication
is implemented in #130/#137.

## Decision

The tests remain suitable for a development branch as opt-in, intentionally red
acceptance work. Existing regression behavior stays green on both tested systems.
Do not make the failing acceptance command a required default CI check or close
#140 yet. Agree the service DBMS CLI/schema, rerun the currently unreached
assertions against the integrated service, and verify concurrent/interrupted
execution with the new DBMS path before claiming complete server E2E acceptance.

This is Linux arm64 headless verification, not x86 CI, native GUI verification,
DBMS restart persistence, or the complete `.tc` Tactical App.
