# tacc — `.tc` compiler

Compiles a `.tc` program into a `.bc` file per `spec/bytecode.md`.

## Scope

The whole grammar of `spec/language.md`:

- functions with parameters and an optional return type, calls between `.tc` functions (`CALL`);
- `let` / `const` local variables of type `Int`, `Bool`, `String`, `Float`, and assignment;
- arithmetic, comparison, equality, and logical negation with the precedence from the spec;
- `if` / `else if` / `else`, `while`, `return`;
- Runtime calls `ns.func(...)` to the functions in `spec/runtime-api.md`.

The semantic checks (types, scopes, `const`, return paths) are listed in `spec/language.md` →
"Semantic rules". Classes, structs, and a standard library are not part of the language yet.

## Structure

| File | Stage |
| --- | --- |
| `src/main/antlr/tacc/Tc.g4` | ANTLR 4 grammar: lexer and parser rules, generated into `TcLexer` / `TcParser` |
| `Parse.kt` | runs the generated lexer and parser, reports the first error as `LexError` / `ParseError` |
| `AstBuilder.kt`, `Ast.kt` | parse tree → AST |
| `Checker.kt` | semantic analysis: names, scopes, types, local slots |
| `CodeGen.kt`, `Bytecode.kt` | AST → instructions and constant pool |
| `BytecodeWriter.kt` | module → `.bc` bytes |
| `Main.kt` | command line |

Code generation follows `spec/language.md` → "Compilation notes":

- parameters occupy locals `0 .. param_count-1`, `let`/`const` variables the following slots in
  order of declaration (one slot per declaration);
- `a > b` is `b < a`, `a <= b` is `!(b < a)`, `a >= b` is `!(a < b)`, `a != b` is `!(a == b)`,
  `-x` is `0 - x` for Int or `FNEG` for Float; reversed comparisons use a temporary local to preserve left-to-right evaluation;
- every call leaves one value on the stack, so a call used as a statement is followed by `POP`;
- a function without a return type returns `Int 0` (`PUSH_CONST 0` + `RET`) on `return;` and at the
  end of its body;
- `if` and `while` use `JMP` / `JMP_IF_FALSE` with absolute offsets inside the function's code; a
  branch that always returns is not followed by a jump, so no jump targets the end of the code.

Lexing and parsing are generated by ANTLR 4 (Gradle `antlr` plugin, `org.antlr:antlr4` 4.13.2) from
`Tc.g4`, which follows `spec/language.md` → "Grammar" rule by rule; the EBNF in the spec stays
authoritative. `./gradlew installDist` and `./gradlew test` generate the lexer and parser into
`build/generated-src/antlr/main` first; only `antlr4-runtime` is shipped with `tacc`. Syntax errors
are reported in the form `expected <what>, found <token>` instead of ANTLR's default messages.

## Build and run

Requires JDK 17+. From `compiler/`:

```sh
./gradlew installDist
build/install/tacc/bin/tacc ../tests/hello/hello.tc build/hello.bc
```

On Windows use `.\gradlew.bat installDist` and `build\install\tacc\bin\tacc.bat`.

Usage: `tacc <input.tc> <output.bc>`. Write the output under `build/` (ignored by git), not under
`tests/`: `.bc` files in `tests/` are not ignored.

## Testing

`./gradlew test` runs the unit tests in `src/test/kotlin`:

- `LexerTest`, `ParserTest` — tokens of the generated lexer, precedence and associativity, syntax errors;
- `CheckerTest` — positive and negative tests of types, scopes, `const`, calls, and returns;
- `CodeGenTest` — exact instruction sequences, `hello.tc` byte for byte against
  `tests/hello/hello.bc`, and the behavior of compiled programs.
- `DataHelpersTest` — signatures of the Observation/Target data helpers, their type errors and
  lowering, and compilation of every `.tc` source under `app/`, `docs/examples/` and `tests/`.

Program behavior is checked with a small reference interpreter in `TestSupport.kt`. It is a test
oracle for the compiler only, written against `spec/bytecode.md`; `tacvm` remains the VM.

CTest runs the full chain `.tc` → `tacc` → `.bc` → `tacvm` and compares standard output with
`expected.txt`:

| Test | Program | Needs in the VM |
| --- | --- | --- |
| `hello_e2e` | `tests/hello` | `PUSH_CONST`, `CALL_RUNTIME`, `POP`, `RET` |
| `control_flow_e2e` | `tests/control-flow` | locals, arithmetic, comparisons, jumps (#62) |
| `language_example_e2e` | `tests/language-example` (example from `spec/language.md`) | the above and `CALL` |
| `data_tc_e2e` | `tests/data-tc` (Observation/Target, malformed inputs, type errors) | Float and the data helpers in Runtime |

The VM tests in `tests/vm` (`vm_*_e2e`) also compile their programs with `tacc`.

## Error reporting

Errors are reported as `<file>:<line>: error: <message>` on stderr, with exit code 1. Compilation
stops at the first error.

## Float (issue #107)

`Float` literals have digits on both sides of the decimal point (`1.5`); arithmetic
and comparison operands must both be `Float` (no implicit `Int` conversion).
The compiler emits v2 bytecode if any Float construct is present, otherwise v1.
Float constants are binary64 little-endian tagged `0x02`, and instructions use
`FADD` through `FCMP_LT` (`0x11`–`0x17`). Reversed comparisons preserve the
left-to-right evaluation order using temporary local slots.

Run `./gradlew test` (including `FloatTest`), then validate the coordinate
example against a v2-capable `tacvm`. The VM from PR #116 must be merged or
built separately before an actual end-to-end test can succeed.

## Observation and Target data (issue #132)

The Runtime signatures of `spec/runtime-api.md` → "Minimal String data helpers" are registered in
`RuntimeFunctions` with their static types: `json.arrayLength`, `json.arrayObject`, `json.getInt`,
`json.getFloat`, `json.getString`, `json.quote`, `text.concat`, `text.fromInt`, `text.fromFloat`,
and the existing `camera.detectMarkers() -> String`. No syntax, opcode or bytecode version was
added: each call lowers to `CALL_RUNTIME` like any other Runtime function. A call whose result is
`Float` (`json.getFloat`) makes the module v2, as for every other Float construct.

Wrong arity, wrong argument types, a `Float` result used with `Int`, `String + String` and
unknown helper names are compile-time errors.

## Language limitations (issue #144)

What the final Analyzer and Map sources have to work around. These are properties of the `.tc`
language and its Runtime, not of the Go reference implementation in `app/map/*.go`:

- **No structs, arrays or collections.** Domain records are separate scalar locals and
  parameters; detector results and messages are JSON `String` values read and built with the
  data helpers. A detector array has at most 72 objects; every helper input and output is at
  most 65,536 bytes.
- **Flat JSON only.** The helpers accept objects of String and number fields, and arrays of
  such objects. Nested values, `true`/`false` and `null` are errors.
- **No recoverable errors.** Malformed JSON, a missing key or a wrong field type raises a
  RuntimeError and `tacvm` exits with status 1. Map cannot yet skip one bad update and keep its
  window; this is an open question in `spec/runtime-api.md`. `runtime.ipc_send` still reports
  delivery failure as `-1` instead.
- **No string operations besides the helpers:** no length, indexing, substring, search or
  ordering; only `==` and `!=`. `String + String` is an error; use `text.concat`.
- **No numeric conversions.** There is no `Int` ↔ `Float` conversion, implicit or explicit,
  and no rounding function. Integer JSON tokens can be read as `Float` with `json.getFloat`.
- **No math library:** no `sin`, `cos`, `sqrt`; Analyzer computes them with series in `.tc`.
- **Literals:** `Float` literals need digits on both sides of the point and have no exponent;
  String escapes are only `\"`, `\\` and `\n`, so other characters are written as UTF-8.
- **Control flow:** `if` / `else if` / `else`, `while` and `return`; no `&&`, `||`, `for`,
  `break` or `continue`. Conditions are combined with nested `if` or Bool locals.
- **Limits:** 255 parameters and local slots per function, 65,536 distinct constants and
  functions per module.
- **No device APIs yet:** location, heading and time come from fixtures until #134.
